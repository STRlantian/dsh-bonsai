# 上下文与缓存影响实验（A/B）

目的：回答一个具体问题 —— **这套树的注入，对上下文开销和 prompt 缓存命中到底有多大影响？**

## 方法

三个脚本，两步跑完，全程本地：

| 脚本 | 作用 |
|---|---|
| `scripts/ab-drive.mjs` | 以浏览器同样的网关协议（`session/create` / `session/prompt` / `session/page`）驱动一个 web 实例跑固定问题 |
| `scripts/bench-cache.mjs` | 解码会话日志，从 `assistant/message.usage` 取真实用量，算每轮命中率与注入量 |
| `scripts/ab-run.ps1` | headless 版本（当前环境下用不了，见"已知限制"） |

步骤：

```powershell
# 1) 两个隔离 profile：一个不装插件，一个装
dsh --profile aboffw --from-default-profile web
dsh --profile abonw  --from-default-profile web
dsh plugin --profile abonw add file:D:\dsh-token-tree\plugin

# 2) 各起一个实例
dsh --profile aboffw --no-open --port 19501
dsh --profile abonw  --no-open --port 19502

# 3) 同一组问题，各跑 8 轮
node scripts/ab-drive.mjs --port 19501 --token <token> --label baseline
node scripts/ab-drive.mjs --port 19502 --token <token> --label plugin

# 4) 对比
node scripts/bench-cache.mjs <baseline-session-dir>
node scripts/bench-cache.mjs <plugin-session-dir>
```

问题列表刻意**混合跳脱与关联**：哈希表 3 连问 → 天气（跳脱，触发工具）→ 回到哈希表 2 连问 → 线段树（跳脱）→ 树状数组（关联）→ 跨分支汇总。只问一个话题测不出挂接决策，只跳话题测不出检索。

## 实测结果（2026-10-21，deepseek-flash）

### 汇总

| 指标 | 基线（无插件） | 插件 | 变化 |
|---|---|---|---|
| 轮数 / 步数 | 8 / 10 | 8 / 11 | +1 步 |
| 注入块 | 0 | 7 | — |
| 注入 token（合计） | 0 | 2,719 | 388/轮 |
| 新增 input token | 11,751 | 29,216 | **+149%** |
| 缓存读取 token | 143,744 | 232,320 | +62% |
| 输出 token | 745 | 1,362 | +83% |
| 命中率 | 91.78% | 91.69% | **−0.09 pt** |

### 逐轮（input / cached）

```text
基线                          插件

t2   230 /   8960            t2   257 / 10368

                              t3  9367 / 22016   ← 多跑了一步

t6   156 /  19584            t6   417 / 32512
```

## 结论

1. **不伤缓存**：命中率 91.78% → 91.69%，差 0.09 个百分点，在噪声内。原因是注入追加在**消息末尾**，system + 历史的公共前缀没变。
2. **但注入块本身永远不被缓存**：它每轮都在末尾新增，所以每轮多出约 250–400 个"全新 input"token。这正好等于注入量，符合预期。
3. **主要成本来自步数，不是注入**：插件那次在工具轮多跑了一步，一步就是约 9.4k 的新 prompt。8 轮里 1 步 = 总开销差距的一半以上。
4. 长上下文场景下（本仓库主会话 39 万 token）命中率仍在 99.9%，说明结构本身不破坏缓存；成本随会话变长线性增长的是"缓存读取"，而缓存读取单价远低于新 input。

## 已知限制

- `scripts/ab-run.ps1`（headless 路线）在此环境不可用：账号凭据只允许"桌面端/网页端"这个目的地使用，headless 进程被拒绝（`ACCOUNT_SIGN_IN_REQUIRED` / `MISSING_CREDENTIAL`）。
- 样本只有 8 轮 × 2 次，步数差异会显著影响汇总值；要可比，需固定在**无工具**的问题集上，或重复多次取中位数。
- `session/follow` 是流式端点，普通 HTTP POST 打不开（"stream methods must be opened through the stream carrier"）；驱动器目前只靠 `session/page` 轮询 `turn/end` 判断完成。

## 花费

19 次 assistant 调用，约 4.1 万 input、2.1k output，按 deepseek-flash 定价远低于 1 元。

## 实验二：长上下文召回（19 轮）

设计：先以对话形式给出 **14 条独特事实**（项目代号、数据库文件名、认证容差、备份时间、错误码起点、连接池/限流…），再问 **5 个只能回引早期信息**的问题。两臂同一脚本、同一问题集。

```powershell
node scripts/ab-drive.mjs --set recall --port 19501 --token <token> --label rbase
node scripts/ab-drive.mjs --set recall --port 19502 --token <token> --label rplug
node scripts/bench-cache.mjs <session-dir>
```

### 结果

| 指标 | 基线 | 插件 |
|---|---|---|
| 轮数 | 19 | 19 |
| **召回正确** | **5/5** | **5/5** |
| 新增 input | 4,265 | 9,166（+115%） |
| 缓存读取 | 175,104 | 253,184 |
| 注入 token | 0 | 7,700（428/轮） |
| 命中率 | 97.62% | 96.51%（**−1.11 pt**） |

两臂的答案完全一致（`data/qingsong.db` / `30` / `03:15` / `40001` / `20 与 60 次每分钟`）。

### 结论

- **质量没有变差，也没有变好**：19 轮、约 2.5 万 token 的上下文里，全量历史本来就装得下，模型不需要"选择性召回"。
- **成本确实更高**：新增 input 翻倍，且命中率掉约 1 个百分点 —— 因为注入块每轮都是**全新的尾部内容**，永远不会命中上一轮的缓存前缀。
- 所以这个规模下，插件是**纯成本、零收益**。收益要等"历史塞不下、必须丢弃"的时候才可能出现，而本 harness 的 `compaction-basic` 在 web profile 里默认 `disabled`，短期内造不出那个场景。

### 顺手发现的坑

- 早期把提示写成"记一个事实：…"时，模型把它理解为**写文件**动作，在仓库里生成了一个乱码 `AGENTS.md`（已删除）。现在的提示改成陈述式，并显式禁止调用工具/改文件。
- `session/page` 是**滑动窗口**，按 `turn/end` 计数会失效（窗口外的事件会掉出去），必须按**最大 seq** 判断新回合。

- 实验二：38 次调用，约 43 万 input（多数命中缓存）。
- 两次合计按 flash 定价约 **¥1 左右**，在 5 元预算内。

## 实验三：工具优先模式（不注入大块，只给一行提示）

动机：既然每轮注入 400+ token 的块"纯成本"，那就把检索改成**模型主动调用工具**，每轮只追加一行提示（约 57 token），让它知道旧历史要自己取。

### 实现

- `autoInject: false`（默认）、`retrievalHint: true`（默认）；
- 提示只在树里有 ≥6 个节点时出现，避免首轮噪音；
- 一条真实的提示：

```text
[token-tree] Older turns may be summarised or trimmed. Before answering anything that
depends on earlier details, call retrieve_context (weighted over this conversation's
tree) to pull them back; do not guess from the summary.
```

> 坑：`cordis/bundle.patch.yml` 里原本硬编码了 `autoInject: true`，会覆盖代码默认值。第一次跑"工具优先"实验时注入的仍是 400+ token 的大块，就是这个原因。已改成 `autoInject: false`。

### 结果（19 轮，同一组 14 事实 + 5 召回问题）

| 指标 | 基线（无插件） | 工具优先 |
|---|---|---|
| 召回 | 5/5 | **5/5** |
| 注入 token / 轮 | 0 | **57**（大块模式是 428） |
| 新增 input | 4,157 | **3,926（−5.6%）** |
| 缓存读取 | 176,000 | 207,104 |
| 命中率 | 97.69% | **98.14%（+0.45 pt）** |

结论：**工具优先把注入成本从 428 → 57 token/轮（−87%），召回不变，命中率不降反升。** 大块自动注入在这个规模下确实是纯成本。

### 但这次没证明"收益"

`compaction-basic` 虽然在配置里 `disabled: false`、`maxTokens: 8000`，但两臂日志里**没有任何 `compaction/*` 事件** —— 压缩根本没触发，历史始终完整。所以：

- 模型从头到尾**一次也没调用** `retrieve_context`（没必要，全历史都在）；
- 提示行的价值（"把被压缩掉的事实取回来"）**尚未被验证**。

要验证，得先让压缩真的发生（可能需要更低的 `maxTokens`、或压缩只在溢出重试时生效）。这是 harness 侧配置问题，不是插件问题。

## 压缩（compaction）的触发条件

读 `@deepseek-ai/dsh-compaction-basic/lib/index.js` 得到的确切规则。压缩有两条触发路径：

1. **每步压力检查**：`agent/pre-step` 时调用 `compactIfNeeded(agent, "pressure")`；
2. **请求溢出恢复**：`agent/request-error` 且 `code === CONTEXT_WINDOW_EXCEEDED` 时压缩后重试。

压力路径的判据（`resolveCompactSpec`）：

```text
messageBudget  = contextWindow − request.maxTokens          ← 预留补全额度
pressureBudget = messageBudget − headroomTokens
thresholdTokens = floor(min(contextWindow × thresholdRatio, pressureBudget))
retainTokens    = floor(messageBudget × retainRatio)        ← 保留逐字尾部
触发条件        = 会话估算 token ≥ thresholdTokens
约束            = retainTokens < thresholdTokens（否则直接报配置错误）
```

实测环境参数：

| 变量 | 值 | 来源 |
|---|---|---|
| `contextWindow` | **1,000,000** | `request/context` 事件 |
| `request.maxTokens`（预留补全） | **256,000** | `request/header.config.maxTokens` |
| `thresholdRatio` 默认 | 0.8 | 插件默认 |
| 推导出的阈值 | `(1,000,000−256,000) × 0.8 ≈ 595,200` | — |

所以 2.5 万 token 的会话差了两个数量级，**永远不会触发**。这也解释了为什么把 `maxTokens: 8000` 写进配置毫无效果 —— 那个字段是"单次摘要的最大 token"，不是上下文窗口。

要在便宜的规模触发，配方是**调比例而不是调窗口**：

```yaml
- id: compaction-basic
  name: "@deepseek-ai/dsh-compaction-basic"
  disabled: false
  config:
    thresholdRatio: 0.01     # 阈值 ≈ 7,440 token
    retainRatio: 0.005       # 保留尾部 ≈ 3,720，必须 < 阈值
```

按此配置，14 条事实喂到第 5～6 轮就会触发第一次压缩。

### 但压缩仍未真正触发（2026-10-22 复核）

| 事实 | 证据 |
|---|---|
| headless profile 里 `compaction-basic` **是启用的** | `--dump-config` 无 `disabled: true` |
| web profile 里被 **web-app 层禁用** | dump 注释 `patched by @deepseek-ai/dsh-web-app` + `disabled: true` |
| 用 profile 补丁重新启用**能进合成配置** | dump 显示 `disabled: false` 且带 `thresholdRatio: 0.01` |
| 但会话里**依然没有** `compaction/*` 事件 | 19 轮、累计 prompt ≈ 18 万 token，0 事件 |

所以配方本身是对的（阈值 ≈ 1 万），但插件实例**没有真正跑起来**。最可疑的是 `compaction` 是一个 `cordis:group`（`isolate: { compaction: true }`）：组内那个隔离实例才是 agent 使用的，而它仍处于 disabled；顶层补丁只复用了同名行。

要真正验证，得改 **web-app bundle 层**（`@deepseek-ai/dsh-web-app` 的 patch），而不是 profile 层；或改用 headless profile（但本机 CLI 鉴权被账号策略挡住）。这件事**搁置**，等找到 web-app 层的可配置入口再继续。

## 实验 4：压缩之后还能召回吗（2026-10-22）

### 先解决"怎么按需压缩"

`/compact` **不是普通消息**。把它当 prompt 发出去，模型会当作问题回答（第一版实验就是这么失败的：`compaction/end` 事件 0 个）。

真正的入口是 `commands/execute`：

```js
rpc('commands/execute', { agentId: sessionId, line: '/compact', submittedAttachments: [] })
// → { kind: 'success', text: 'Compacted 24 history items (~2216 tokens).', sourceEventSeq: 115 }
```

它是 `@deepseek-ai/dsh-command-compact` 暴露的手动压缩命令，内部调 `ctx.compaction.compactNow(agent, signal, commandId)`，**完全绕过阈值**。
这意味着压缩从"等上下文压力"变成"随时可复现的动作"，实验条件终于可控了。

### 两次基线（只有压缩，没有插件）

| 轮次 | 事实形态 | `/compact` 结果 | 压缩后 5 题召回 |
|---|---|---|---|
| baseline | "请记住"清单式 | `Compacted 24 items (~2,216 tok)` | **5/5** |
| baseline2 | 埋在叙述里（日志、压测报告、运维同步） | `Compacted 29 items (~4,945 tok)` | **5/5** |

**结论（重要且不利于本插件）**：在这个规模下，压缩摘要**把事实都保住了**。
即使事实是顺带提到的（`kuroshio_user.db`、`45 秒`、`03:20`、`41000`、`90 次/分`），
摘要仍然逐条保留，模型无需检索即可答对。

这与前三次实验的结论一致：**在几千到两万 token 的上下文里，树带来的是成本，不是召回收益**。
树的"逐字保留原始节点"这个优势，只有在摘要**开始丢信息**时才兑现 —— 也就是事实数量多到摘要必须压缩成纲要的时候。

### 还没做的那一步

把事实规模拉到**摘要一定会丢**的量级（例如 30 条分散事实 + 噪声轮次），再比较：

- 基线（无插件）：压缩后逐题作答的命中率；
- 树（插件开）：允许 `retrieve_context` 后的命中率与工具调用次数。

成本估计：约 30–60k token/臂，两臂合计约 ¥1～2（在既定预算内）。
脚本已就绪：`scripts/ab-compact.mjs --filler N --tools`。

### 30 条事实的那一版：基线直接打满

```
$ node scripts/ab-compact.mjs --port 19522 --token … --label base30 --facts 30 --ask 10 --filler 10

[base30] /compact → success: Compacted 82 history items (~2133 tokens).
[base30] recall after compact: 10/10
[base30] retrieve_context calls: 0
```

30 条分散事实（6 个模板 × 5 组编号）、10 轮填充、一次 `/compact`，之后抽 10 题：**10/10 全中**。

基线已经在天花板，再跑"树"臂只可能持平或更贵（多出工具调用），因此**没有再跑**。

### 三轮实验合起来的结论

| 事实规模 | 压缩量 | 基线召回 | 是否值得跑树臂 |
|---|---|---|---|
| 5 条（清单式） | 24 项 / 2,216 tok | 5/5 | 否（天花板） |
| 5 条（埋叙述里） | 29 项 / 4,945 tok | 5/5 | 否（天花板） |
| 30 条（模板生成） | 82 项 / 2,133 tok | 10/10 | 否（天花板） |

**这个 harness 的压缩摘要相当忠实**：它保留了具体文件名、数字、时间、目录名，甚至编号变体。
在能负担得起的规模（≤ 数万 token）里，压缩**没有制造出"事实丢失"的场景**，所以树没有可测的用武之地。

诚实结论：**加权对话树在当前 harness 的上下文策略下没有可测收益**。
它换来的东西（逐字节点、主题召回、人工分叉）要等到"摘要必须丢细节"的规模才有价值 ——
那一档需要会话长度远超本次实验的量级（估计数十万 token、上百轮），单次成本已超出本项目预算。

如果未来要做，最省的验证方式是**离线合成**：把真实长会话喂给 `retrieveContext`
（已有 `scripts/bench-retrieval.mjs`，100% recall @217 token vs 全量 4,182 token），
再与"摘要 + 保留尾部"的召回去比，不需要模型在环。

### 顺带的产品改动：自动提示改为按需出现

既然短对话里这些机制都是纯成本，每回合的检索提示（`retrievalHint`）也改成了条件触发：

```ts
if (state.compacted !== true && tree.nodes.size < this.config.hintMinNodes) return undefined
```

- 会话**被压缩过**（`compaction/start|end` 事件）→ 立刻恢复提示：此时旧事实真的可能不在上下文里；
- 或节点数 ≥ `hintMinNodes`（默认 40，约 20 轮）→ 提示；
- 否则**一行都不发**，短对话零额外 token。

对应测试：`tests/plugin.test.ts` 的 "with injection off the hook appends one short retrieval hint instead"。

## 实验 5：可审计的复测（2026-10-22，用户质疑后重做）

前几轮有两处方法学问题，先记下来：

1. README 曾把实验 3 的 4,157 抄进实验 2（实验 2 实际是基线 4,265 / 插件 9,166），已改；
2. 复核用的脚本一开始用"消息里是否含 token-tree 字样"和 `data.message.source` 判断注入，**两个都错**：工作区路径 `D:\dsh-token-tree` 出现在普通消息里，而日志的真实形状是 `data.source.kind`。按错误口径，基线和插件组都显示"注入 1 次"。

所以这一轮换了做法，脚本是 `scripts/ab-rigorous.mjs`：

- **交替排程** A/B/B/A/A/B，避免"先跑完一组再跑另一组"的时间漂移；
- 每题按**植入值精确子串匹配**判分，逐题打印；
- token 数取自每条 `assistant/message.data.usage` 求和；
- 注入数按 `data.source.kind === 'token-tree'` 统计，并额外交叉验证 `request/context` 里是否出现 `retrieve_context` 字样；
- 全部原始数据落到 `docs/experiments/*.json`（含 session id），可自行用 `scripts/bench-cache.mjs` 复算。

### 轮次 A：默认配置（`hintMinNodes: 40`）

| 组 | 跑数 | 正确 | 新增 input / run | 命中率 | 实际注入 |
|---|---|---|---|---|---|
| 基线（无插件） | 3 | **15/15** | 3,057 | 97.94% | 0 |
| 插件 | 3 | **15/15** | 3,198 | 98.11% | **0** |

10 条事实 → 约 21 个节点 < 40，**提示被门控住，一行都没发**。所以两组的差异只能算噪声（+4.6%），
这正好验证了默认配置的行为：**短会话里插件成本严格为 0**。

### 轮次 B：强制发提示（profile 里 `hintMinNodes: 1`）

| 组 | 跑数 | 正确 | 新增 input / run | 命中率 | 实际注入 |
|---|---|---|---|---|---|
| 基线（无插件） | 2 | **10/10** | 3,017 | 98.01% | 0 |
| 插件 | 2 | **10/10** | **2,978（−1.3%）** | 98.30% | **15/run ≈ 57 tok/行** |

注入确实到达了模型：每个插件 run 的会话日志里有 15 条 `source.kind = token-tree` 的用户消息，
且 `request/context` 记录里出现 `retrieve_context` 字样 **27 次**（基线组 0 次）。

### 这一轮能说和不能说

- 能说：**召回没有差异**（基线 25/25、插件 25/25，共 10 个 run）；提示本身约 57 token/行，
  在实测用量里没有造成可辨识的输入增长（−1.3% 属噪声）；默认门控让短会话零成本。
- 不能说：树能让模型答对更多题。这次仍然没有构造出"历史装不下"的场景，所以那部分
  依旧是**未证实**，不是"已证伪"。
- 树的价值仍集中在两块已确认的东西上：**结构编辑/导航 UI**，以及**离线检索质量**
  （`bench-retrieval.mjs`：200 节点树 recall@12 = 100%，217 token vs 全量 4,182）。

## 实验 6：阈值该定在多少（离线，零模型成本）

提出的想法：每轮不拼接全部，只取匹配度 > 0.5 的前若干个；找不到再回退到更早的对话。

`node scripts/bench-retrieval.mjs --sweep`（200 节点 / 40 分支 / 预算 400 / topK 12）：

| 相关性下限 | recall | 每查询返回节点 | 空结果率 |
|---|---|---|---|
| 0.12（当前默认） | **20/20** | 12.0 | 0% |
| 0.20 | **20/20** | 9.7 | 0% |
| 0.30 | 8/20 | 4.0 | 0% |
| 0.40 | 0/20 | 1.2 | 0% |
| **0.50** | **0/20** | 0.2 | **90%** |
| 0.60 | 0/20 | 0.0 | 100% |
| 0.70 | 0/20 | 0.0 | 100% |

注意：这个 `threshold` 卡的是**合成得分**（相关度与路径权重混合后的值），不是原始余弦。
换个口径再看 `--cosine`（原始余弦，目标节点）：

| 指标 | 数值 |
|---|---|
| 目标节点的平均余弦 | **0.43** |
| 单题目标余弦区间 | 0.33 ～ 0.55 |
| 余弦 ≥ 0.5 的节点数 | 每题 0 ～ 4 个 |

**所以"匹配度 > 0.5"会让检索在九成查询里空手而归**，回退逻辑会变成主路径。
原因不是算法差，是这套局部哈希嵌入的余弦本身就不高（0.33～0.55 就是"相关"的量级）。

### 结论：可以更好，但要换结构而不是抬阈值

| 你的想法 | 判断 | 依据 / 改法 |
|---|---|---|
| 每轮额外跑一个"简短总结" | ⚠️ 分情况 | 用**模型**生成 = 每轮多一次调用，正是实验 1 证明最贵的那种；用**本地确定性摘要**（首句 / 关键词 / 截断）则可行：**用摘要匹配、返回原文** |
| 不跑总结，直接用提问 | ✅ 就是现状 | 节点文本本身含问题与回答 |
| 只取匹配度 > 0.5 的前几条 | ❌ 数据不支持 | 合成得分口径下 90% 空；余弦口径下均值仅 0.43 |
| 分两闸：先准入再排序 | ✅ 推荐 | 准入用**原始余弦 ≥ 0.30**（召回仍 20/20），排序用现有合成得分，最后按预算裁剪 |
| 找不到就回退更早的对话（工具调用） | ⚠️ 顺序要改 | 工具结果是**最贵、复用率最低**的内容；回退阶梯应为：置顶/约束 → 祖先链（root→focus） → 最近 N 轮 → 最后才是旧工具结果 |

可实施的默认组合（建议）：`准入余弦 0.30` + `排序用合成得分` + `预算 400～600 token` +
`回退阶梯按上面的顺序`。验收方式就是重跑 `--sweep` 与 `--cosine`，不需要模型在环。

### 实现与验收（2026-10-22）

准入阈值做成了可配置项：`weights.admitRelevance`（默认 **0.3**），运行时也能在「设置 → 检索准入阈值」改。
它只决定**谁有资格进入排序**，排序本身仍用原来的合成得分；置顶节点和 `mustIncludeIds` 直接跳过准入。

`node scripts/bench-retrieval.mjs --admit-sweep`（200 节点 / 40 分支 / 预算 400 / topK 12）：

| 准入阈值 | 召回 | 每次返回节点 | 空结果率 |
|---|---|---|---|
| 0（关闭） | 20/20 | 12.0 | 0% |
| 0.20 | 20/20 | 10.8 | 0% |
| 0.25 | 20/20 | 8.4 | 0% |
| **0.30** | **20/20** | **7.2** | **0%** |
| 0.35 | 18/20 | 4.4 | 10% |
| 0.40 | 10/20 | 2.0 | 40% |
| 0.50 | 6/20 | 1.2 | 70% |

**0.3 是拐点**：召回不降，返回节点从 12.0 降到 7.2（少约 40% 上下文）。

回退按提出的思路实现为"**空格重试**"：准入后如果一个候选都没有，自动以 `admitRelevance: 0` 重跑一次，
并在结果里标 `counts.relaxed = true`。**空缓冲被视为失败，而不是"精确"**。

一个必须记下的风险：0.3 是在**关键词式查询**上标定的。自然语句查询的相关节点余弦常见只有 **0.28～0.29**
（测试里 `attention token weight` 对相关内容只有 0.290），刚好会被 0.3 挡掉，而某个无关节点反而过关。
所以：

- 想要更稳，用 **0.2～0.25**（召回仍 20/20，节点 8.4～10.8）；
- 想要更省，0.3 可用，但要接受"偶尔挡掉真正相关的那条"；
- 0.4 以上不建议。

对应测试：`tests/retrieve.test.ts` 的 "admission prefers precision but never returns an empty buffer"
（覆盖：精确命中被准入、无关节点被拒、空手时 relaxed 重试、置顶绕过准入）。

### 本地摘要参与匹配（`summary` + `summaryMatch`）

长节点（> 40 token）写入时生成**首句摘要**（≤ 40 字）并单独存一份摘要嵌入；检索时
`relevance = max(cos(原文), cos(摘要))`，命中后仍返回**原文**。全程本地，无额外模型调用。

`node scripts/bench-summary.mjs`（6 个主题，事实放长节点首句，后面接大段无关填充）：

| 配置 | recall | 中位排名 |
|---|---|---|
| 短节点 + 摘要开 | 6/6 | 1 |
| 长节点 + 摘要**关** | **1/6** | 3 |
| 长节点 + 摘要**开** | **6/6** | **1** |
| 长节点 + 摘要关 + 无准入 | 6/6 | 4 |
| 长节点 + 摘要开 + 无准入 | 6/6 | 1 |
| 超长(×20，约 3,000 token) + 摘要关 | 2/6 | 8 |
| 超长(×20) + 摘要开 | 4/6 | 1 |

要点：
- 摘要必须**只取首句**。先前的"前 120 字"把第二句填充也带了进来，余弦从 0.31 掉到 0.18，几乎无效。
- 长节点靠原文匹配时余弦只有 0.13（远低于准入线），所以**摘要不是锦上添花，是这类节点能否被召回的前提**。
- 边界：若首句本身带很长的元信息前缀（"项目背景记录（无需操作…）：备份窗口固定在 03:15。"），摘要会连前缀一起截，命中率下降。

### 回退阶梯：最终只保留"放宽准入"一级

原计划是"置顶/约束 → 祖先链 → 最近 N 轮 → 旧工具结果"。实测发现**祖先链这一级不可达**：
凡是能让"放宽准入"也为空的场景（所有分支被忽略或隐藏），祖先链会被同一组标记跳过，永远返回空。
因此最终只有一级回退——**准入后为空就去掉门槛重跑一次**，结果里标 `counts.relaxed = true`。
由于排序本身含路径权重，放宽后重排出来的天然是离当前节点最近的节点（等价于"更早/更近的对话"），
不必再写一条祖先链逻辑。代码里保留了这段结论的注释，避免以后重复实现。

### 端到端验证（工具路径）

`node scripts/e2e-retrieve.mjs --port <p> --token <t>`：3 条带大段填充的事实 → 强制模型调用 `retrieve_context`：

```text
retrieve_context calls: 1
tool result: Retrieved 2 node(s), 107/2000 tokens, 6 dropped, injected=true.
             - n8 question w=0.7171 tokens=46
             - n3 answer w=0.3723 tokens=61
```

**2 个节点进上下文、6 个被丢弃**，模型照抄了返回的节点编号 —— 准入与摘要链路在实际会话里生效。

## 实验 7：新模式对命中率 / 缓存 / 输入的影响（2026-10-22）

三臂，同一批问题、交替顺序 **A/B/C/C/B/A**，每臂 2 跑；脚本 `scripts/ab-retrieval.mjs`，
原始数据 `docs/experiments/round3-retrieval.json`（含 session id）。

| 臂 | 配置 | 正确 | 新增 input/run | 缓存命中 | 检索调用 | 返回节点 | 返回 token |
|---|---|---|---|---|---|---|---|
| A | 不检索（凭历史回答） | **8/8** | **2,687** | 96.82% | 0 | 0 | 0 |
| B | 旧模式（准入 0、摘要关） | **8/8** | 6,167 | 96.09% | 8 | 55 | 6,178 |
| C | **新模式（准入 0.3、摘要开）** | **8/8** | **4,520** | **97.07%** | 8 | **32** | **2,578** |

**新模式 vs 旧模式**（这才是这次改动的效果）：

- 新增 input **−27%**（6,167 → 4,520）；
- 缓存命中 **+0.98 pt**（96.09% → 97.07%）；
- 返回节点 **−42%**（55 → 32），返回 token **−58%**（6,178 → 2,578）。

**检索 vs 不检索**（诚实的一面）：

- 命中率**没有差别**（三臂都 8/8）—— 会话只有 4 条事实、几千 token，历史本来就在上下文里；
- 但每次检索要多一次工具往返，所以"检索"整体仍比"不检索"贵 **+68%（4,520 vs 2,687）**。

结论：**这次改动显著降低了检索路径的成本（−27% 输入、−58% 注入 token、缓存命中还更高），
但它改变不了"短会话里根本不需要检索"这个前提**。收益仍然只在"历史装不下"的场景里才可能出现。

## 实验 8：用官方 tokenizer 决定"要不要注入"（2026-10-22）

用户提供了 `deepseek_v4_tokenizer.zip`（HF `tokenizer.json`，128k vocab / 127,741 merges / 字节级 BPE）。
仓库里没有 JS tokenizer，随附的 Python 也没有 `transformers`，所以直接实现了一个**纯 JS 读取器**
（`src/core/tokenizer.ts`，无原生依赖、无网络），只做计数、不做编码。

### 先验证它准不准

`node scripts/tokenizer-check.mjs --tokenizer ...`：

| 文本 | 字符 | tokens | 字符/token | 旧估算(chars/2.5) | 官方/估算 |
|---|---|---|---|---|---|
| 英文散文 | 70 | 12 | 5.83 | 28 | 0.43 |
| 中文散文 | 28 | 17 | 1.65 | 12 | **1.42** |
| 中英混合 | 36 | 24 | 1.50 | 15 | 1.60 |
| 代码 | 30 | 18 | 1.67 | 12 | 1.50 |
| JSON | 62 | 19 | 3.26 | 25 | 0.76 |

- 所有 piece 都在词表内（未知 0），合并按 merges 排名执行，特殊 token 先切分；
- 结论：**英文被低估 57%，中文被高估 42%** —— 一个常数确实不可能同时服务两种语言。

### 性能（每回合都要数一遍上下文）

`node scripts/tokenizer-perf.mjs`：加载 116 ms；20k 字符 27 ms；60k 74 ms；200k 254 ms。
因此实现里按**消息 id 增量缓存**：每回合只为新消息付费。

### 决策怎么改

| 之前 | 现在 |
|---|---|
| 节点数 ≥ 40 才发提示（代理指标） | 有 tokenizer 时：**实测上下文 ≥ `hintAboveTokens`（默认 12,000）** 才发 |
| | 无 tokenizer 时：仍按节点数，行为不变 |
| 会话被压缩过 → 立即发 | 同左（压缩本身就说明历史已经丢了） |

配置：`tokenizerPath`（默认指向 `~/.dsh/token-tree/deepseek_v4_tokenizer/tokenizer.json`）、`hintAboveTokens`。
接口可观测：`GET /api/token-tree/settings` 返回 `tokenizer: { path, state }`，实测 `state: "ready"`。

### 谁更准：用账单口径对账

判据不是"谁看起来合理"，而是 **provider 实际计费**：每一步的 `usage.inputTokens + cacheReadTokens + cacheWriteTokens`
就是这次请求的 prompt 大小。取"只新增 1 问 + 1 答"的回合（单步、无工具调用），delta 就应当等于这两段文本的 token 数。

`node scripts/token-accuracy.mjs`：

| 会话 | 可比步数 | 官方 tokenizer MAE | 旧估算 MAE |
|---|---|---|---|
| `79f59106` | 7 | **47.7** | 83.3 |
| `fcff813b` | 3 | **32.3** | 178.7 |

逐步看（`fcff813b`，中文为主）：

| 步骤 | 计费 Δ | 官方计数 | 旧估算 |
|---|---|---|---|
| 1 | 462 | 397（−14%） | 606（**+31%**） |
| 2 | 426 | 396（−7%） | 608（**+43%**） |
| 3 | 420 | 422（+0.5%） | 630（**+50%**） |

**结论：官方 tokenizer 准，旧估算系统性地高估中文约 45%**（它把每个汉字当 1 token，实际约 1.6 汉字/token）。

两点保留：
1. 偏差不为零的部分（官方那 −7%～−14%）来自我重建请求时漏掉的框架级内容（系统提示、工具定义、运行时上下文），不是分词错误；
2. 这是**我们自己实现的 JS 读取器**，没能和 HF 参考实现在本机逐字节对拍（环境里没有 `transformers`）。但它对计费用的贴合在几个百分点内，这正是预算判断需要的性质。

另有一个方法上的坑值得记下：`37bfb65c` 这类会话里每步都有框架注入的运行时上下文/技能目录消息，我的重建只取 `source.kind === 'user'`，
于是 delta 里混进了没被计入的文本，两边的误差都会爆到 1000+ —— 那是重建口径的问题，不是分词器的问题。

### 字符级比例会不会变，能不能在线学

**会变，而且幅度很大**：同一个汉字在不同上下文里可能独占一个 token，也可能并进更大的词；英文更明显
（`a` 是 1 token，`attention` 也是 1 token）。实测同一批文本的字符/token 从 **1.50（中英混合）到 5.83（英文散文）**，
差了近 4 倍。所以"一个常数"必然错，但**分成宽字符（CJK/全角）与窄字符两类**就能贴近。

`src/core/ratio.ts` 用**在线最小二乘**拟合 `tokens ≈ a·宽字符 + b·窄字符`：每次拿到精确计数就 `observe()` 一次，
从先验 `a=0.6, b=0.2` 起步，样本越多越准。它的定位是**只做预筛，不做最终判断**：

- 预筛：估算值远低于阈值（< 0.6×阈值）时直接跳过，不数整个上下文；
- 逼近阈值时仍用官方 tokenizer 精确计数；
- 每次精确计数都会回喂给比例，形成闭环。

三者在真实计费口径下的对账（`scripts/token-accuracy.mjs`）：

| 会话 | 可比步数 | 官方 MAE | 学习比例 MAE | 旧单常数 MAE |
|---|---|---|---|---|
| `79f59106` | 7 | **47.7** | 51.9 | 83.3 |
| `fcff813b` | 3 | **32.3** | 44.7 | **178.7** |

结论：
- **官方最准**（残差主要来自重建请求时漏掉的框架级内容）；
- **学习比例紧随其后**（中文为主的会话 44.7 vs 官方 32.3），并且**第一步就有值**（从先验起步）；
- **旧单常数最差**，中文会话里高估近 1 倍。

### 宿主里的实际表现

配置 `tokenizerPath` 后，第一次 `agent/pre-step` 会加载（116 ms）并把样本喂给比例：

```text
start:       {"wide":0.6,"narrow":0.2,"observations":0}      state: unknown
after turn1: {"wide":0.6,"narrow":0.2204,"observations":4}   state: ready
after turn2: {"wide":0.639,"narrow":0.2204,"observations":5}
```

同时 `recountNodeTokens()` 把树上所有节点的 `tokens` 由估算改成实测 ——
**节点预算、注入块长度、payload 里的 token 数从此都是计费等价的值**。

一个实现细节值得记下：最初把预筛写在精确计数之前，结果短会话永远走不到计数，`state` 一直是 `unknown`、
比例永远停在先验。改成预筛阶段也先**加载并对最新 1–3 条消息**学习（`warmRatio`），两个问题一起消失。

### 模型升级后 tokenizer 会不会失准

**会。** `tokenizer.json` 与模型版本绑定：词表变了（增删 token、改预分词正则），同一段文本的 token 数就变，
典型幅度几个百分点，遇到新词表 + 中文/代码较多的文本可以到 10%+。这对本插件的影响面是：

| 用途 | 对漂移的敏感度 |
|---|---|
| 提示阈值（`hintAboveTokens`） | 低 —— 阈值本身漂移 ±10% 只是"早/晚一轮" |
| 节点预算（`tokenBudget`） | 低 —— 差几成不影响选择顺序 |
| 判断"能否塞进某个硬上限" | **高** —— 需要留 10% 余量 |

所以显式加了一个**漂移监测**（`TokenTreeService.observeBilling`），思路是拿"账单增量"比"计数增量"：

```text
ratio = Δ(billed input+cacheRead+cacheWrite) / Δ(counted)
```

只用增量是因为账单里还有系统提示、工具定义、运行时上下文这些我们不统计的固定开销 —— 用绝对值比会得到
26 倍这种荒谬数字（第一版就这么错的）。连续 3 个样本的均值落到 [0.85, 1.2] 之外时打一条 warn，
建议更新 `tokenizerPath`。`GET /api/token-tree/settings` 里暴露 `drift: { samples, ratio }`。

**它只告警，不自动修复**：真正跟上新模型只能换 `tokenizer.json`（配置项可换，不用改代码）。
另需注意：学习比例拟合的是"字符 → 我们的 tokenizer"，**不会自动跟随账单**，所以漂移时它一起漂。

对应测试：`tests/tokenizer.test.ts` 的 "the drift monitor compares billed growth against counted growth"
（模拟账单按 1.1× 增长，断言监测结果 ≈ 1.1）。

### 按模型版本自动选 tokenizer

每代模型有自己的一套词表，所以插件不再接受"一个文件路径"，而是接受**一个版本号**，自己去目录里找文件
（`src/plugin/tokenizer-select.ts`）：

| 配置 | 含义 |
|---|---|
| `tokenizerVersion: auto`（默认） | 选磁盘上**最新的**代数 |
| `tokenizerVersion: 4` / `'v4'` | 指定代数；没装就回退到最新，并在日志/settings 里说明 |
| `tokenizerVersion: deepseek-r1` | 从模型名解析：`r1` 归到 **v3** 词表 |
| `tokenizerVersion: off` | 彻底关掉精确计数，回到估算 |
| `tokenizerPath` | 显式文件，优先级最高（兼容旧配置） |

目录布局（默认 `$DSH_HOME/token-tree`）：

```text
token-tree/
  deepseek_v3_tokenizer/tokenizer.json
  deepseek_v4_tokenizer/tokenizer.json
```

宿主实测（`GET /api/token-tree/settings`）：

```json
"tokenizer": {"path":null,"state":"ready","version":4,"available":[3,4],"requested":"auto"}
```

### 模拟一场对话：v3 与 v4 的差别、以及旧估算错在哪

`node scripts/simulate-conversation.mjs --dir <token-tree> --threshold 150`，10 轮中英混合对话
（含报错、配置 JSON、工具输出）：

| 轮 | 文本长度 | 精确(v4) | 精确(v3) | 学习比例 | 旧估算 |
|---|---|---|---|---|---|
| 1 | 93 | 28 | 28 | 24 | 34 |
| 2 | 85 | 38 | 38 | 35 | 50 |
| 3 | 43 | 27 | 27 | 25 | 34 |
| 7 | 212 | **84** | **84** | 59 | **53** |
| 10 | 50 | 36 | 36 | 26 | 35 |
| 合计 | — | **323** | **323** | — | — |

三个结论：

1. **v3 与 v4 在这批文本上计数完全相同**（divergence 0）—— 两代共用同一套词表。
   所以"按版本选文件"目前是**保险**而不是立刻的收益；一旦哪天词表真的变了，它才生效。
2. **旧估算在中文段落高估**（34 vs 28、50 vs 38），**在 JSON/代码上低估**（53 vs 84），
   方向还不一致，所以无法用系数修正。
3. 阈值 150 时：**精确计数在第 6 轮触发，旧估算在第 4 轮就触发** —— 两轮的差距，等于白白多发两行提示。

再模拟"tokenizer 过期"（账单按 1.3× 计数）：漂移监测得到 `1.30` → **触发告警**。
这也说明为什么报警要留着：v3/v4 一样不代表下一代一样。

一个使用注意：漂移监测只在**真的做了精确计数**时采样（即上下文接近或超过阈值），
短会话里 `samples` 会一直是 0 —— 这是设计如此，不是坏了。

## 实验 9：最终配置的端到端效果（2026-10-22）

配置：`autoInject: false`、`retrievalHint: true`、`hintAboveTokens: 12000`、
`admitRelevance: 0.3`、`summaryMatch: true`、tokenizer v4（auto）。

两段，各两跑、交替顺序、脚本判分，账单数字取自 provider 的 `usage`：

### 段一：默认配置（短会话）

| 组 | 正确 | 新增 input/跑 | 缓存命中 | 提示行 | 最终上下文 |
|---|---|---|---|---|---|
| A 不装插件 | **8/8** | 2,461 | 97.89% | 0 | 10,037 |
| C 插件 | **8/8** | 2,507 | **98.10%** | **0** | 11,220 |

差异在噪声内（+1.9% 输入、+0.21pt 命中），**提示一行都没发** —— 短会话零成本，符合设计。

### 段二：把阈值降到 40（强制每轮发提示）

| 组 | 正确 | 新增 input/跑 | 缓存命中 | 提示行 | 最终上下文 |
|---|---|---|---|---|---|
| A 不装插件 | **8/8** | 2,483 | 97.85% | 0 | 9,851 |
| C 插件 | **8/8** | **2,351（−5%）** | **98.24%（+0.39pt）** | **20**（≈10/跑） | 11,652 |

提示真的注入了（每跑 10 行，共 20 行），成本影响很小：最终上下文 +18%（10 行 × 57 token = 570，
其余差异来自回答长度波动），输入甚至略低（噪声，n=2）。**命中率略升**：提示是稳定前缀，
不破坏缓存。

### 段二之前踩到的真 bug

第一次跑段二时 **0 行提示**，查出来是门槛算错了对象：`agent/pre-step` 的 `decision.messages`
**只含最新那条消息**（实测首轮 394 token），拿它和 12,000 的门槛比，永远不触发 ——
也就是说**提示功能在长会话里也是死的**，只是短会话本来就该"不发"，才没有暴露。

修法：门槛改成 **对话路径上的节点 token 之和**（`conversationTokens`，数据本来就存在树上、
加载 tokenizer 后是实测值），不再依赖 `decision.messages`。修完后宿主实测：

```text
lastHint: {"counted":100,"above":40,"fired":true,"reason":"conversation over threshold"}   hint lines: 1
lastHint: {"counted":90,"above":300,"fired":false,"reason":"conversation under threshold"} hint lines: 0
```

顺带加了一个诊断字段 `settings.lastHint = {counted, above, fired, reason}`，
以后"提示为什么没发"可以直接查，不用猜。

### 结论

- **默认配置下插件是隐形且免费的**：短会话 0 注入、成本与不装插件持平。
- **提示真的发出来时**：≈57 token/轮，对缓存命中略有正贡献，对输入量基本无感。
- 召回仍是 8/8 vs 8/8 —— 这些会话还没到"历史装不下"的程度，所以**收益仍未被证明**，
  能证明的是"成本可控"。



















## 实验 10：压缩之后，树还能不能救回细节（2026-10-22）

这是"检索到底有没有价值"的判决实验。两组装**同一个脚本**：把 4 个**精确字符串**塞进工具风格的
长 dump（探针超时 1733ms、sha256 前缀 9f2c41ab77de、灰度批次 rbx-2291、回滚阈值 0.42%），
再接 6 轮无关对话把它们推远，**手动 `/compact`**，然后逐个追问，要求只答原串。

| 组 | 正确 | input/跑 | 提示行 | 真的调用 retrieve_context |
|---|---|---|---|---|
| A 不装插件 | **8/8** | 4,790 | 0 | 0 |
| C 插件（提示阈值 200） | **8/8** | 6,995 | 13 | **0** |

**结论：依然无法证明收益，而且这次插件更贵。**

1. **压缩摘要把 4 个精确串全都保住了**（连 12 位十六进制前缀都对），所以基线天花板就是 8/8 ——
   没有可改善的空间。这是**天花板效应**，不是机制无效。
2. **提示发了 13 次，模型一次都没调用检索工具**（两次跑都是 0）。提示在真实使用中是**惰性的**。
3. 成本上插件 +46% input（含跑间方差：C 两次是 5,218 / 8,772）。

### 那到底什么情况下树才有用

只有当**上下文真的装不下**时才有意义，而当前 harness 的压缩摘要太忠实，装得下。
要造出收益场景必须人为降级摘要（改 `retainRatio` 或截断摘要），那不是真实配置，
测出来的数字也没有说服力。

所以到此为止，**诚实的结论**是：

- 树的确定价值 = 图形化编辑（分叉/改挂/隐藏/跳转）+ 精确 token 记账；
- 检索/反思这一路的成本是**可测的**（+46% 输入），收益**未被证明**；
- 默认配置因此保持 `autoInject: false`、提示阈值 12,000（短会话零成本），
  让它在不需要时不花钱、需要时不添乱。

## 实验 11：hook 里到底能不能"用检索替代拼接"（2026-10-23）

设计初衷是"检索一个子集替代全量历史"。要成立，插件必须**拿到并能改写完整历史**。
在 `agent/pre-step` 里实测两件事。

### 1. `decision.messages` 只是新增消息

| 轮次 | 收到的 messages | 字符数 | 来源 kind |
|---|---|---|---|
| 1 | 3 条 | 1,749 | user, runtime-context, skill-catalog |
| 2 | **1 条** | 15 | user |
| 3 | **1 条** | 15 | user |
| 4 | **1 条** | 22 | user |
| 5 | **1 条** | 22 | user |

同期树里累计约 150 token，且模型确实能接着上文回答 —— 所以历史不是从这里来的。

### 2. `decision` 只有两个字段

| 轮次 | 字段 | messages 大小 | 条数 |
|---|---|---|---|
| 1 | kind, messages | 3,536 字节 | 3 |
| 2 | kind, messages | 220 字节 | 1 |
| 3 | kind, messages | 220 字节 | 1 |

没有任何 history / context 容器。宿主把历史拼进 prompt 发生在 hook **之后**，
插件既看不到也改不到。宿主自己减少上下文靠压缩（包内可见 `contextFold` 相关符号；
桌面版实测触发过 2 次、共 73,838 token）。

### 结论

- 准确说法：**插件能改"这一步要追加的新消息"，不能改 prompt 里的历史**。
- 所以"检索替代拼接"在当前扩展点**不可实现**，不是没做。
- 注入只能增加 input：实测 +115%（19 轮）到 +149%（8 轮）；命中率变化在 ±0.5pt 噪声内。
- 唯一能真正减少 input 的杠杆是**按实测 token 提前触发 `/compact`**。
- 诊断字段：`settings.lastPrompt = {count, chars, kinds}`、`settings.lastDecision = {keys, sizes}`，
  日后可随时复核这两条结论。

## 压缩本身要花多少（2026-10-23，真实会话日志）

压缩不是免费的：`compaction/summary` 前面必然有一次带 `usage` 的 assistant 消息。
扫了 120 个会话、69 个 compaction 事件、12 次 summary，全部有账单：

| 会话 | prompt token | 输出 | 其中命中缓存 |
|---|---|---|---|
| 38b5a580 | 11,453 | 58 | 11,264（98.3%） |
| 56272a95 | 81,084 | 1,054 | 80,640（99.5%） |
| 37bfb65c | 726,962 | 760 | 726,784（99.98%） |
| d5bdaca3 | 15,130 | 4 | 14,976 |
| fa42cc54 | 11,046 | 2 | 10,880 |

平均 prompt **196,886 token**，就是整段历史；两次事件间隔约 2 秒。

两种机制要分清：

- `compaction/prune`：**不调模型**，机械丢弃（工具输出等），事件里带 `shadowedTokenCount`。
- `compaction/summary`：**调模型**，读全量历史写 checkpoint（`## Primary Request and Intent ...`）。
  `/compact` 与 `compactNow` 走这条（通常先 prune 再 summary）。

推论：

1. 自动压缩每次触发 = 一次全历史调用。钱不多（99% 是缓存读），但是真实开销与一次往返延迟。
2. 它省下的也主要是**便宜的缓存 token**（会话命中率 97–99%），所以"省钱"的边际收益很小；
   压缩真正的价值是**别撞上下文上限**、降低延迟。
3. 因此默认冷却定为 **10 分钟**，且默认关闭（阈值 0）。压得太勤只是反复付调用费。
4. 细节不丢：树里存原文，压缩后的第一条提示带"折叠节点索引"指路。

## 实验 12：压缩后索引 vs 裸提示（2026-10-23）

目的：验证"压缩后给一张折叠节点索引"能否让模型真的回树里查（A = 裸提示，C = 索引）。

### 第一轮：无效

| 组 | 正确 | retrieve_context | 其它工具调用 | input/跑 |
|---|---|---|---|---|
| A 裸提示 | 8/8 | 10 | 97 | 6,749 |
| C 索引 | 8/8 | 3 | 95 | 7,342 |

两处污染：

1. 提问里写成了「不要调用工具以外的任何东西都可以」（病句），模型于是用 `read` / `pwsh`
   去磁盘上找事实，每组 45–50 次工具调用，实际调用的是 `read×8`、`pwsh×6` 这类；
2. 两组都是 4/4 —— 说明**根本不需要检索**。

### 第二轮：天花板确认（决定性）

同样先放 4 个精确事实、6 轮填充、`/compact`（Compacted 22 items / ~1,005 tokens），
然后**禁用一切工具**再问：

```text
HIT expect=1733        tools=0 answer="1733 毫秒。"
HIT expect=9f2c41ab77de tools=0 answer="9f2c41ab77de"
HIT expect=rbx-2291    tools=0 answer="rbx-2291"
HIT expect=0.42        tools=0 answer="错误率超过 0.42% 即回滚。"
```

**4/4，零工具调用。** 压缩摘要把这些精确串都保住了 —— 这是第三次遇到同一个天花板
（实验 10 追问 4 个精确串也是 8/8）。

### 结论

1. 在**对话摘要式压缩**下，索引没有可发挥的余地：原文本来就没丢，模型不需要查。
   这不是索引无效，而是**没有需求**。
2. 索引的成本是确定的（每次压缩约 300 token，只发一次），收益在这个场景下为 0。
3. 真正可能出现需求的场景是 **`compaction/prune`**：它机械丢弃工具输出，摘要不会复述这些
   内容。要验证索引，必须把事实放进**真实的工具输出**、让 prune 把它 shadow 掉，再问。
   这还没做。
4. 因此 `compactionIndex` 保持默认开启但只是一次性 300 token 的保险；不宣称它已被证明有效。

### 第三轮：把事实塞进工具输出（2026-10-23）

思路：让模型用 `pwsh` 真的执行命令，把 4 个精确事实放进**工具输出**，再 `/compact`，
期待 `compaction/prune` 把工具结果 shadow 掉，这样原文才真的从 prompt 消失。

| 组 | 正确 | retrieve_context | 其它工具 | prune 事件 | shadowed token |
|---|---|---|---|---|---|
| A 裸提示 | 4/4 | 10 | 16 | **0** | **0** |
| C 索引 | 4/4 | 14 | 16 | **0** | **0** |

**prune 一次都没发生。** 短会话里 `/compact` 只跑摘要（Compacted N items），
没有可裁剪的旧工具输出 —— 于是"内容被机械丢弃"这个前提**根本没成立**，
两组都能从上下文里直接答对，实验再次落空。

顺带得到一个正面的结论：**模型只要被明确要求，就会大量调用 `retrieve_context`**
（A 组 10 次、C 组 14 次，每次都成功取回正确原文）。
所以检索工具本身是可用的，缺的从来不是"能不能查"，而是"想不想查"。

### 三轮之后的总结

| 想造的困境 | 现实 |
|---|---|
| 摘要丢细节 | 两次实测都保住了（实验 10、12 第二轮） |
| prune 丢工具输出 | 短会话里 prune 不触发（实验 12 第三轮） |
| 索引提升检索率 | 没有需求，测不出差异 |

要真正造出"细节确实不在 prompt 里"的场景，需要一个**很长**的会话（工具输出累计到
prune 窗口之外），这会消耗显著预算。在此之前，诚实的结论是：
**树的价值是编辑与记账；检索能力可用但收益未被证明。**

## 实验 13：隐藏工具是唯一被测出来的省钱手段（2026-10-23）

装配里各部分的大小（两句话的会话实测）：

| 组成 | 字符 | 占比 |
|---|---|---|
| 工具 schema（37 个） | 34,271 | 83% |
| 系统提示词段落（22 段） | 5,736 | 14% |
| contexts | 995 | 2% |
| variables | 57 | — |

最大的几个工具：`pwsh` 3,495、`workflow` 3,389、`schedule_create` 3,143、
`schedule_update` 2,403、`retrieve_context` 1,295、`subagent_fork` 1,268。

用宿主最弱的机制 `agent.ctx.tools.restrict({ deny })`（宿主注释称为"只能移除工具"）隐藏 9 个：

| | 工具数 | schema 字符 | 本次 prompt |
|---|---|---|---|
| 基线 | 37 | 34,271 | 10,453 tok |
| 隐藏 9 个 | 28 | 21,224 | **7,076 tok** |

**每轮省 3,377 token（−32%），而且不是一次性的。** 这是整个项目第一次测出真实收益。

两个实现要点：

1. `agent/created` 的载荷是 `{ agent }`，不是 agent 本身；`agent.ctx.tools.restrict` 才存在。
2. `restrict()` **会校验工具名**：名单里有一个不存在的名字（比如 `subagent`）就整批拒绝，
   并返回"known global tools"清单。所以这是可选功能，且 UI 会把失败原因显示出来。

代价要说清楚：隐藏的是**能力**。`workflow`、`schedule_*`、`subagent_fork`、`ask_user_question`、
`get_goal`/`update_goal` 都是真的用不了。默认不隐藏任何工具。

缓存注意：必须**每会话固定**同一份名单，否则前缀一变，省下的 token 会以缓存失效还回去。

## 实验 14：用 surfaceOp replace 折叠历史（2026-10-23）

这是**第一次把历史真正从模型视野里拿掉**，而且**不调用模型**。机制来自官方开源契约
（`SurfaceOp` 包含 `append` 与 `{ op: replace, startSeq, endSeq }`）与两个社区插件
（dsh-delete-turn、dsh-clear-tool-results）：日志只追加，模型可见的消息由 surface 派生。

脚本：两轮各自让模型跑一次 400 行输出，第三轮总结。阈值 50、保留 1 轮。

| | 不折叠 | 折叠 | 省下 |
|---|---|---|---|
| turn 1 | 13,193 | 13,094 | 99 |
| turn 2 | 18,486 | 17,750 | 736 |
| **turn 3** | **20,510** | **17,586** | **2,924（−14.3%）** |

折叠只写一条带 replace 意图的事件，**没有模型调用**；诊断里 `folded: 1`，
surface 上能看到占位符「[已折叠] … 原文保存在对话树中，需要细节时调用 retrieve_context 取回」。

### 踩到的约束

第一次尝试被宿主拒绝：

```text
session append cannot reenter while another append is being published
```

原因是在 `session/event` 监听里直接 `session.append` —— 事件还在发布中。改成 `setTimeout(…, 0)`
延后到下一个宏任务即可。这条值得记下来：**任何"在监听里写日志"的插件都会遇到**。

### 与自动压缩的对比

| | 自动压缩 | surface 折叠 |
|---|---|---|
| 模型调用 | 一次，读全量历史 | **无** |
| 减掉什么 | 区间 → 模型写的摘要 | 区间 → 一行占位符 |
| 原文 | 日志与树里还在 | 日志与树里还在 |
| 成本 | 有 | 一条 append |

所以对"不要整段历史搬上去"这个目标，折叠是更合适的工具；压缩适合"需要保留语义摘要"的场合。

## 实验 15：折叠整轮，以及模型到底会不会去查（2026-10-23）

把整轮（用户消息 + 助手回复 + 工具调用/结果）换成一个占位行，然后测两件事：
**省不省 token**，以及**事实被折走之后模型会不会去 `retrieve_context`**。

脚本：5 轮。轮 1 闲聊（开场轮永远受保护），轮 2 放「探针超时 1733」，轮 3 放「批次 rbx-2291」，
轮 4 和第 5 轮问同一个问题。折叠在 `turn/end` 之后写入，所以**轮 4 还看得见事实，轮 5 看不见**。

| | 轮 4（事实可见） | 轮 5（事实已折叠） |
|---|---|---|
| 折叠开 | 「1733」· retrieve=0 | 「1733」· **retrieve=1** |
| 折叠关 | 「1733」· retrieve=0 | 「1733」· retrieve=0 |

**结论：事实被折走之后，模型确实会去调 `retrieve_context`，并且答对。**
不折叠时它一次都不查 —— 因为它本来就知道。这说明折叠没有把模型逼向瞎猜，而是把它导向了检索。

这同时回答了之前几轮实验留下的问题：「什么时候该查」不是靠提示词催出来的，
而是**上下文里真的没有**时自然发生的。

### 三个只有实机才会暴露的约束

1. `user/message` 载荷必须有 `role` 与 `id`，否则请求被 422 拒绝
   （`messages[2]: missing field role`）；
2. 区间必须按 **surface 顺序**给（`visible` 可能是 `…18,40,35,37…`），
   按 seq 排序会得到 `start 35 (index 7) after end 40 (index 6)`；
3. 第一个 surface 节点是系统提示词，只能由 `system/message` 针对该节点重写，
   所以**开场轮不折叠**；折叠只从第 2 轮开始。

另外：折叠是延后一轮生效的（在 `turn/end` 写），这一点在设计提示语时要记住。

## 实验 16：发布版在真实会话里的表现（2026-10-24）

用户在另一个工作区用 npm 上的 0.1.4 跑了一个 17 轮的会话（音乐理论 → 算法，历史 50,645 tok）。

### 分树

| 问题 | 修复前 | 修复后 |
|---|---|---|
| 介绍一下算法竞赛中的对拍 | 挂到**和弦回答**（0.382） | 根（新分支） |
| 线性代数中的矩阵求导 | 挂到**KMP 回答** | 根 |
| 介绍 trie | 根 | 挂在 AC 自动机下 |
| 详细介绍动态规划 | dijkstra 回答 | 不变 |

原因分两层：

1. **纯虚词二元组**：「中的」「的对」这类由虚词字符组成的 bigram 被当成词面证据。现在按字符规则过滤，不依赖词表；
2. **单个通用词不足以换支**：`算法` 在 32 个节点里出现在 8 个，仍然通过了 1/3 的门槛。现在门槛是 **1/10**（下限 2），并且**跨分支跳转需要两个具体共享词或一个 ≥3 字的词**，否则分数打 0.3 折。留在当前线程不受此限（那由 `newTopicBelow` 管，追问常常只共享一个词）。

### 折叠与缓存（同一会话的真实计费）

```text
call  1   10,757 tok  hit 92.8%
call  5   33,093 tok  hit 57.2%   ← 第一次折叠之后：14,149 token 变成新输入
call 10   55,598 tok  hit 99.7%   ← 折叠前峰值
call 11   47,156 tok  hit 98.5%   ← 第二次折叠：删掉 8,442 token，缓存仍是 98.5%
call 18   47,797 tok  hit 99.1%   ← 之后稳定在 47–48k，不再增长
```

**结论**：折叠确实把 prompt 摁在 ~47k（不折叠会一路涨到 ~90k），且**第二次之后的折叠几乎不掉缓存**（命中率 98.5–99.7%），因为折叠点靠后，前面的前缀不变。

**但第一次折叠很贵**：它落在第 2 轮，位置太靠前，后面 14k 的缓存全部失效，那一轮出现 57.2% 的命中率。这是一次性的；之后每折一轮省 8k 左右，很快回本。

可改进方向（未做）：第一次折叠可以等「可折区间 ≥ 尾部长度的一半」再触发，避免在缓存收益最差的时候动前缀。

## 实验 17：中途取消的回合不进树（2026-10-24）

扫描本机 40 个会话的 `turn/end` 原因分布：

```text

```

`aborted` 的载荷形如 `{"kind":"aborted","reason":{"kind":"user"}}`，就是用户点了停止。

处理规则：节点在发消息时就建（回合内的工具结果要有地方挂），`turn/end` 若是 `aborted` / `interrupted` 就把这个问题节点标记为隐藏 —— 它连同**已流出的半截回答**一起从树、列表、图形和 token 统计里消失，但可以从回收站恢复。`error` 保留问题（用户确实问了，可能要重试），`completed` 不动。

顺带修正：`historyTokens` 现在跳过隐藏节点，隐藏的分支不再计入折叠阈值。

## 实验 23：折叠的真机 A/B（同工具、同问题、只改折叠）

方法：同一个宿主、同一套工具（两次运行都是 28 个工具，脚本断言一致）、同一组问题；每组的会话里
先种 6 个"事实 + 约 300 字说明"，再回头追问其中 3 个。两组唯一的差别是折叠开关，通过插件自己的
设置路由写入。顺序 ABBA，两组各 2 次。

| 配置 | 步数 | prompt/步 | 新增输入 | 缓存读取 | 折叠次数 | 答对 |
|---|---|---|---|---|---|---|
| 关闭 | 18 | 10,345 | 3,672 | 182,538 | 0 | 6/6 |
| 开 3,000/留 2 | 18 | 9,392（−9.2%） | 11,106（+202%） | 157,950 | 12 | 6/6 |
| 关闭 | 18 | 10,088 | 4,680 | 176,904 | 0 | 6/6 |
| 开 600/留 1 | 20 | 9,379（−7.0%） | 17,091（+265%） | 170,496 | 12 | 6/6 |

关键发现：**prompt 变小了，但新增输入（缓存未命中的部分）涨了 2–2.6 倍** —— 每次折叠都改写
prompt 前缀，之前的缓存随之失效。按"缓存读 ≈ 输入价 1/10"折算，开折叠反而更贵：

| 配置 | miss 等价值 | 相对 |
|---|---|---|
| 关闭（3,000 组） | 3,672 + 18,254 = 21,926 | — |
| 开折叠（3,000 组） | 11,106 + 15,795 = 26,901 | **+23%** |

含义：折叠的收益要求"折叠次数少、被折内容大"。短会话里每轮都折一次，缓存重置的成本超过
prompt 缩小的收益。长会话（本仓库 155 轮那种）折叠相对罕见，收益才会占上风。

局限：每组仅 2 次运行、6 轮对话；折算系数 0.1 是假设，不是账单。
脚本：`scripts/ab-fold-live.mjs`，原始数据 `docs/experiments/fold-live*.json`。


## 实验 24：把落点判断整轮交给模型（含新话题）

做法：`any` 模式下，提示里同时给出候选问题与两种标记——`[attach:nX]` 表示依赖某条，
`[attach:root]` 表示新话题；本地仍给默认值，模型沉默时用默认。每个会话先种 5 个话题，
再交替 5 个延续探测与 5 个无关新话题，共 2 个会话。

| 指标 | 结果 |
|---|---|
| 延续句写了 `[attach:nX]` | 10/10 |
| 其中指向正确话题 | 10/10 |
| 新话题写了 `[attach:root]` | 10/10 |
| 新话题最终挂在根 | 10/10 |
| 开场（种话题）轮用 root | 4/5 |

这些落点是**模型驱动**的：原始日志里每个新话题轮的助手消息都确实带了 `[attach:root]`。

局限：2 会话 × 10 探测、单一模型；"新话题应挂根"是脚本设计，不是人工标注；脚本早期版本只解析
`[attach:nXX]`，把 root 标记当成沉默，那一版统计已作废。


### 实验 19 的更正（用对齐后的探针复测）

原来的 43% 与后来的复测不一致，原因是两个测量错误：

1. `probe-retrieval-rank` 用"样本列表按下标对齐问题列表"的方式配对，一旦有消息被跳过就错位，曾给出 **1%** 这种明显错误的读数；
2. 该探针在**消息入树之前**就调用检索，而生产里 `agent/pre-step` 是在消息入树之后，两者相差很大（9% vs 23%）。

| 指标 | 数值 |
|---|---|
| 父回答出现在检索结果 | **23%**（50/219） |
| 父回答排第一 | **11%**（23/219） |
| 强制注入（`mandatoryContext`）后 | ≈99%（接线保证） |

结论不变、但表述要改：**打分检索本身没有测出增益**，99% 来自强制注入。43% 这个数不再引用。


## 实验 25：换分词器能不能提高挂接准确率（负结果）

离线指标：重放会话 37bfb65c，对每个问题调用检索，看"问题所挂的父回答"是否出现在结果里、排第几。
同一会话、同一进程参数，只换特征提取。

| 特征来源 | 父回答进结果 | 排第一 | 耗时 |
|---|---|---|---|
| 字符二元组（现状） | **23%**（51/219） | **10%**（23/219） | 基线 |

## 实验 26：BM25 替代现有词面分（中性结果）

做法：给每个节点算词频（复用 `tokenize` 的过滤），用 BM25（k1=1.2, b=0.75）替换

|---|---|---|
| 现状（最大 IDF 比） | **14/18（78%）** | **14/15（93%）** |
| BM25（按候选最大值归一） | 13/18（72%） | 13/15（87%） |
| BM25（按问题 IDF 总和归一） | 13/18（72%） | 13/15（87%） |

## 实验 27：候选块只在"不确定"时发送

"不确定"不是一个概率，而是三条可解释规则之一：

```text
问题按本地规则留在当前线上，且
  · 没有强证据（共享的具体词 < 2 且最长共享词 < 3 字），或
  · 分数低于 attachThreshold（0.18）
→ uncertain
主动改挂（跳分支）、新话题（挂根）、手动锚点 → 确定
指代闸（"它怎么编"）→ 不确定（模型可以确认指代对象）
```

按会话重放，统计有多少轮会发送候选块（每块约 147 token）：

| 会话 | 不确定轮次 | 结论 |
|---|---|---|
| 37bfb65c（写代码） | 0/259（0%） | 全部确定 → 省下约 38,000 token |
| 2ba794ae（学习：注意力机制） | 18/18（100%） | 全部不确定 → 没有节省 |
| 另 3 个写代码会话 | 256/256（100%） | 全部不确定 → 没有节省 |
| 一个小会话 | 0/4 | 全部确定 |

结论：这个门控**因会话类型而异，两极分化**，不是稳定的百分比。学习类会话里它基本不省
（因为问题很少重复上一轮用词），写代码会话里视"是否频繁开新分支"而定。默认仍保留
`attachGate: always`；把它设成 `uncertain` 适合以工具/任务为主的会话。


## 实验 28：让模型在回答末尾写"方面摘要"

做法：提示里追加一行，要求回答末尾写 `[summary: 2–4 个短语，逗号分隔，≤40 字]`；插件把它从正文剥掉，
存成节点摘要，并在候选列表里显示为"问题（含 摘要）"。目的：让"我讲了 A，其中提到 B 和 C"这类回答
在候选列表里可见，追问 B/C 时模型能选回这条回答。

代价：每轮多约 30–40 个输出 token；候选列表每条多约 20–30 token（10 条约 +250）。
收益（待测）：候选列表从"只有问题"变成"问题 + 涉及方面"，指代/子概念追问更容易挂回原回答。


### 实验 28 的结果（18 问学习会话，两遍 A/B）

| 组 | 挂接正确 | 标记 | 写了摘要 |
|---|---|---|---|
| 不开摘要 | **15/18** | 18/18 | 0/18 |
| 开摘要 | 14/18 | 18/18 | 18/18 |

遵从率没有问题（要求写就都写了，样例："注意力定义, QKV与softmax, Transformer…"），
但**正确率没有提升**（15 → 14，差 1 题，在 18 条样本上是噪声）。

### 实验 28b：专门构造的 B/C 场景（仍然失败）

构造：第 1 轮让回答明确提到 Q、K、V；随后**分别**问"那 Q/K/V 具体是什么"。期望三次追问都挂在
第 1 轮回答下（兄弟节点），而不是串成 Q→K→V。位置编码再重复一次（正弦编码 / 可学习编码）。

先说测量错误：第一轮的"以后回答控制在 120 字"指令被分类成**话题**（不是约束），于是多出一对
问答，期望轮次整体错一位，第一版评分（0/5）因此无效。按真实树重新对齐后：

| 组 | 正确 | 实际挂法 |
|---|---|---|
| 无摘要 | **1/5** | Q→第1轮回答 ✓；K→Q 的回答 ✗；V→根 ✗；正弦→上一轮 ✗；可学习→上一轮 ✗ |
| 有摘要（7/7 都写了摘要） | **1/5** | 同上，V 挂到 K 的回答上 |

结论：**摘要没有解决问题**。两个原因：

1. **指代闸挡住了**："那 K 具体是什么"被判定为指代（含"什么/具体"），直接留在当前线，绕过了打分；
2. **即使不挡，打分也分不出来**：A 的回答和 Q 的回答**都包含 K**，词面上无法区分"引入 K 的回答"
   和"提到 K 的回答"；模型也没选对（它把标记指向了上一轮）。

要真正实现"B 和 C 都挂 A 下"，需要一条新规则：**在包含该问题稀有词的多个回答里，选最早引入它的
那一条**（introducer-first），而不是最近的。这条规则本身可以直接在标注集上离线验证。


### 实验 28c：两条新规则都让标注集变差（负结果）

在实现"B 和 C 都挂 A 下"时试了两条规则，各自独立、也可组合：

1. **指代闸放宽**：指代句若点名了"当前回答没提到、但别处回答提到"的词，就不走指代闸，交给打分；
2. **introducer-first**：当前回答没把握时，向上遍历祖先回答，找最早包含问题最稀有词的那条，
   若其分数过阈值就挂上去。

在两套数据上测量：

| 规则 | 18 条学习标注（全部/高置信） |
|---|---|
| 基线 | **14/18（78%）/ 14/15（93%）** |
| 仅放宽指代 | 10/18（56%）/ 10/15（67%） |
| 仅 introducer | 12/18（67%）/ 12/15（80%） |
| 两者 | 9/18（50%）/ 9/15（60%） |

**两条规则都明显更差**，因为学习对话里"同一主题反复出现"是常态：放宽指代会把"接着上一轮"的追问
送去别处，introducer 会把"继续深入"的追问拉回最早的引入处。B/C 场景的离线复算因为轮次映射错误
（会话第一句被当成话题，多出一对问答）没能给出可信数值，暂不作结论。

结论：**B/C 需求与"就近优先"在学习对话里冲突**，不是调一条规则能解决的。代码已回退。


### 实验 28d：子概念指令解决了 B/C（模型侧）

修正了上一轮的测量错误（开场指令现在会被判成约束，不再多出一对问答），并在提示里加一句：

> 问题问的是某条回答里提到的子概念时，挂那条回答（不是刚才那条）。

| 组 | B/C 追问正确（5 次） |
|---|---|
| 无摘要 | **5/5** |
| 有摘要（6/7 写了） | 4/5 |

同一条指令下，18 问学习会话仍是 **15/18**（与之前一致，没有回退）。

结论：解决 B/C 的是**指令里的那句"挂提到它的那条回答"**，不是摘要；摘要反而在一个案例上更差，
因此默认关闭（`attachSummary: false`），保留为可选项。


### 实验 28d（对照修正）

上一版的"1/5"来自结构不同的旧会话（开场指令被当成话题，多了一对问答），不可比。用同一份
7 轮脚本、同一评分方式重测：

| 组 | B/C 追问正确 |
|---|---|
| 无子概念指令（同一会话形状） | **3/5** |
| 有子概念指令、不写摘要 | **5/5** |
| 有子概念指令 + 摘要 | 4/5 |

子概念指令带来 +2/5；摘要再减 1（保留为设置项，默认关）。18 问学习会话在加指令后仍是 15/18。
样本很小（1 个会话、5 次追问），只能算方向性证据。


## 实验 29：给评分公式做消融

在 18 条学习标注上，每次只去掉一个成分：

| 变体 | 全部 | 高置信 |
|---|---|---|
| 完整公式 | 14/18（78%） | 14/15（93%） |
| 去掉 semantic（0.45 那半） | 14/18 | 14/15 |
| 去掉 lexical（0.55 那半） | **11/18（61%）** | 11/15（73%） |
| 去掉长度惩罚 | 14/18 | 14/15 |
| 去掉证据折扣（0.3） | **15/18（83%）** | 14/15 |
| 去掉具体性闸 | 14/18 | 14/15 |

结论（重要且要老实说）：

1. **只有词面分是承重的**，其余三个成分在这份标注上没有贡献；
2. 证据折扣去掉后反而高 1 题（在 18 条样本上是噪声，但至少说明它不是"必要项"）；
3. 这份标注只覆盖**一个学习会话**：它没有超长回答、没有领域通用词，所以长度惩罚与具体性闸
   本来就很少有触发机会。要判断它们是否该保留，需要**写代码会话的标注集**。


## 实验 30：哈希向量与词面分是不是同一生态位

哈希向量（`embedText`）与词面分（lexical）用的是**同一套 token**，只差处理方式：

| 维度 | 哈希向量 | 词面分 |
|---|---|---|
| 输入 | 全部 token（含停用词、虚词二元组） | 过滤后的有效特征 |
| 权重 | 1+log(tf)，无 IDF | 最稀有共享词的 IDF / 问题最大 IDF |
| 聚合 | 全桶求和（宽profile） | 取单个最稀有词（针尖） |
| 归一化 | L2（长度被摊薄） | 除以问题最大 IDF |
| 失败方式 | 常见词 + 哈希碰撞让它"泛泛地接近" | 没有具体词重叠时直接 0 |

三种组合在 18 条标注上的结果：

| 组合 | 全部 | 高置信 |
|---|---|---|
| 0.45×semantic + 0.55×lexical（现状） | 14/18 | 14/15 |
| 语义只在词面为 0 时兜底 | 14/18 | 14/15 |
| 完全去掉语义 | 14/18 | 14/15 |

**结论：在这份数据上，语义半是冗余的**（与消融实验一致）。它理论上覆盖"没有具体词重叠"的场景
（同义改写），但这份标注里没有这种回合，所以三种组合无法被区分。代码保持现状（无实测损害），
不为了"更干净"去改一条无法验证的公式。


## 实验 31：同义改写的标注集（仍然测不出语义的贡献）

构造了 8 条探针（`docs/experiments/paraphrase-labels.json`）：6 条"同义改写"（刻意避开目标回答的技术名词，
例如把"内积"写成"点乘"、把"位置编码"写成"出现的位置"），2 条"控制项"（原样保留关键词，应当命中）。
做法：重放真实学习会话到结尾，再插入一条合成提问，看它挂到哪里。

| 打分模式 | 命中 |
|---|---|
| 0.45×semantic + 0.55×lexical（现状） | 2/8 |
| 语义只兜底 | 2/8 |
| 完全去掉语义 | 2/8 |

**三种模式完全相同**，包括控制项；多数改写落在"上一轮回答"（默认父节点）上。

诊断信息（临时打开打分日志）显示：改写句对**目标回答的分数通常只有 0.02–0.35**，
而默认父节点的分数往往更高，因此过不了"≥0.18 且 ≥ 默认+0.08"这一关。也就是说：

1. 在当前决策规则下，**弱信号永远赢不了"就近默认"** —— 这既解释了本实验，也解释了
   为什么消融里语义半没有贡献；
2. 有一个控制项（"Q 到底表示什么？"）落到根节点，与它 0.07 的分数不符，**这是一个待查异常**，
   在没有定位前不能引用本实验的单项数字。

结论：**同义改写不是当前瓶颈；瓶颈是"弱信号 vs 就近默认"的判定规则**。语义向量的价值要在
"默认父节点明显不相关"的会话里才可能体现，而这种会话目前没有标注集。


### 实验 31b：那个"落在根节点"的异常，查清了

现象：控制项"Q 到底表示什么？"挂到了根，而它的候选最高分只有 0.07，看起来像 bug。

打开带问题标签的打分日志后：

```json
{"q":"Q 到底表示什么？","current":"n38","defaultId":"n38","defaultScore":0.071,
 "threshold":0.18,"margin":0.08,"best":"n38","bestScore":0.071,
 "top":[{"id":"n38","turn":18,"score":0.071},{"id":"n26","turn":12,"score":0.024},{"id":"n22","turn":10,"score":0.02}]}
```

解释（不是 bug）：

1. 18 条回答的公式里都在用 `q`，所以 **df(q) 很高**，具体性闸 `df ≤ max(2, N/10)` 判它"不具体"，
   词面分处处为 0；
2. 语义 cosine 也接近 0（单个字母在 256 维哈希里几乎没有重量）；
3. 于是 bestId 仍是默认节点、且 `defaultScore 0.071 < newTopicBelow 0.15` → **新话题闸把问题挂到根**。

所以这是**设计如此**，不是代码错误；错的是我把"Q"当成了"具体词"来设计控制项 —— 这个控制项无效，已删除，
换成重复一条已验证的控制项（"为什么说内积可以表达相似度？"，两次都命中）。

修正后的同义改写结果：**1/6 命中**（只有目标恰好是最后一条回答的那个"蒙对"），控制项 2/2。
三种打分模式（加性 / 语义兜底 / 去掉语义）在旧版实验中都是 2/8 —— 即**完全相同**，结论不变。

顺带一个真实局限：**公式里的字母记号（q/k/v）在全树都出现，永远过不了具体性闸**，所以
"K 是什么"这类问题在本地规则下不可能挂对；这类回合只能靠模型的 `[attach:nX]` 修正。


### 实验 31c：三条"把含糊追问留在当前线"的规则都失败（负结果）

目标：让"Q 到底表示什么"这类**没有区分性词**的追问不要被新话题闸甩到根。试了三条通用规则：

| 规则 | 结果 |
|---|---|
| 无区分性词就留在当前线 | 没命中："到底/表示"本身也算词，规则不触发 |
| 只在出现**新词**（树里没出现过）时才开新分支 | 仍触发：二元组跨词产生"底表/示什"这种假新词 |
| 没有匹配 + 没有"引入类动词"（介绍/什么是…）就留在当前线 | **修好了这一例，但线上套件抓出两处回归**："今天天气怎么样""锅包肉怎么做"也被留在当前线，挂到了算法回答之下 |

结论：**"含糊追问"与"简短新话题"在二元组特征下不可分**。硬做本地规则，代价是把真正的新话题也留在旧线上，
这比偶尔把追问挂到根更糟（后者模型能改，前者会污染整条分支）。

因此最终只改了**一处**：新话题分支现在标记为 `uncertain`，候选块照常发出，模型可以用
`[attach:nX]` 把误判的追问挪回来。本地判定本身不变（18 条标注仍 14/18），套件 201 全过。


## 实验 32：去掉语义半，改用"词频显著度"（已采纳）

把打分的 semantic 项删掉，改为"该词在候选节点里有多显著"：

```text
score = lexical × prominence × lengthPenalty × evidenceDiscount
prominence = 0.5 + 0.5 × (该词在本节点的出现次数 / 本节点最高词频)
```

| 模式 | 18 条标注 | 高置信 | 同义改写 |
|---|---|---|---|
| 旧：0.45·semantic + 0.55·lexical | 14/18 | 14/15 | 3/8 |
| 去掉 semantic | 14/18 | 14/15 | 3/8 |
| lexical × prominence（新默认） | 14/18 | 14/15 | 3/8 |
| 旧公式 + prominence | 14/18 | 14/15 | 3/8 |

单看默认配置，四者完全相同。但把"改挂边距"放松后，prominence 的价值出现了：

| margin | 旧公式 | lexical × prominence |
|---|---|---|
| 0.08（默认） | 14/18 | 14/18 |
| 0.02 | 13/18 | **14/18** |
| 0.005 | 13/18 | **14/18** |

解释：边距一松，弱信号也会参与竞争，此时"这个词在这条回答里是否中心"能挡住一批误挂。
默认边距下两者等价，但新公式**更简单**（不需要哈希向量参与挂接）且**更稳**（放松边距不掉分），
因此采纳。检索（`core/retrieve.ts`）仍然使用哈希向量，不受影响。

局限：18 条标注仍然是单会话；"prominence 有用"只在"放松边距"的对照里成立，没有在真实默认配置上体现。


### 实验 32b：专门构造的"顺带一提"测试 —— prominence 仍无法决定结果

构造三类确定性场景（`tests/prominence.test.ts`）：

1. **顺带一提**：第 1 轮回答反复讲"缓存"（5 次），第 2 轮回答只顺带提一次，追问"缓存配置容量怎么定"；
2. **双方都反复提**：穿透 / 雪崩两轮都大量出现"缓存"，追问"缓存击穿是什么"；
3. **稀有词**：追问含只在第 1 轮出现的"误判率"。

结果（新公式 `lexical × prominence × penalty × discount`）：

| 场景 | 实际 | 说明 |
|---|---|---|
| 顺带一提 | 停在**当前回答**（不是讲缓存的那条） | 只共享 1 个词 → 非默认节点吃 0.3 折扣 → 分数 ≈0.15 < 0.18 |
| 双方都提 | 停在当前回答 ✓ | 分数接近，边距不足 |
| 稀有词（短回答） | 挂回第 1 轮 ✓ | 证据强（≥2 个具体词）→ 不打折 |

关键结论：**prominence 在"只共享一个词"的场景里不可能生效**，因为
`默认节点免折扣 + 阈值 0.18` 已经把这个场景锁死了：非默认候选的分数上限是
`lexical × prominence × 0.3`，而默认节点同样词面分、却打满 1.0，追赶需要 0.08 的边距。
要让它生效，只能动折扣或阈值 —— 而这两项在此前的实验里都被测出会让分数变差（严格折扣 11/18）。

因此：新公式保留（更简单、放松边距时更稳），但**不要把 prominence 当成"能纠正误挂"的功能**，
它目前只是把弱证据压得更低。


## 实验 33：strong 的第三种定义（负结果）

现状：`strong = shared >= 2 || longest >= 3`。

先澄清一个事实：**中文特征全是二元组（长度恒为 2）**，实测"布隆过滤器…"这类句子的特征长度分布是
`2字:30`，没有 3 字特征。所以 `longest >= 3` 对中文**永远不成立**，中文里 strong 等价于
`shared >= 2`；这个子句只为英文服务（"bloom"、"kmp" 这种 ≥3 字母的实词）。

试了三种替代定义（18 条标注 / 同义改写 8 条）：

| strong 定义 | 18 条标注 | 同义改写 |
|---|---|---|
| 现状：shared≥2 或 longest≥3 | 14/18 | **3/8** |
| 只保留 shared≥2 | 14/18 | 3/8 |
| 改为"匹配词的词频占比 ≥0.5"（tf/maxTf） | 14/18 | **1/8** |
| 两者取或 | 14/18 | 3/8 |

"词频占比"这一版在两个控制项上失败：`"为什么说内积可以表达相似度？"` 与目标回答只共享"内积"，
而"内积"在该回答里不是最高频词 → 判为弱证据 → 打 0.3 折 → 分数掉到阈值下 → 被新话题闸送到根。
也就是说：**用"强调程度"替代"共享词数量"会把正确的匹配也变弱**。

结论：保持现状，但把注释写清楚（`longest >= 3` 只是英文实词规则，不是"中文三字重合"）。


### 实验 33b：evidence = max(共享词数量, 强调占比) —— 有真实效果

按你的定义实现：证据 = max(现有判据, 被匹配词在目标节点里的词频 / 该节点最高词频 ≥ 0.5)。

构造的判别场景（短回答，避免长度惩罚干扰）：

```text
第1轮 问答：缓存按热度淘汰，缓存按过期清理，缓存设上限，缓存命中率要监控。   ← 缓存×4
第2轮 问答：位数组是一串比特。                                            ← 当前回答
追问："缓存怎样更安全"（只共享"缓存"一个二元组，另含树里没有的"安全"）
```

| 配置 | 追问落点 |
|---|---|
| 旧 strong（shared≥2 \|\| longest≥3），margin 0.08 | 停在当前回答（第 2 轮） |
| **strong = max(…, 占比≥0.5)，margin 0.08** | **挂到第 1 轮回答**（讲缓存的那条） |

也就是说：**这个改动确实改变了行为**，而且方向正确（讲得多的那条胜出）。

再看边距的相互作用：

| margin | 旧 strong | max(…, 占比) |
|---|---|---|
| 0.08 | 14/18 · 3/8 | 14/18 · 3/8 |
| 0.04 | — | 14/18 · 3/8 |
| 0.02 | 13/18（此前测） | **14/18 · 3/8** |

采用组合：**strong = max(两读法) + attachMargin 0.02**。标注集保持 14/18（没掉分），
同义改写保持 3/8，而"顺带一提"场景现在能挂到讲得多的那条回答上。

`evidenceOf` 与 `attachmentScore` 现在共用同一套判定（否则 `uncertain` 标记会和决策不一致）。

### 实验 33c：discount = max(discount, 词频占比)（按你的本意，已采纳）

上一版我误做成了把占比加进 **evidence**（strong），需要把边距从 0.08 降到 0.02 才能生效。
按你的本意改成加进 **discount**：

```text
baseDiscount = strong || 是默认节点 ? 1 : 0.3
discount     = max(baseDiscount, 被匹配词的 tf / 该节点最高 tf)
```

| 场景 / 指标 | 结果 |
|---|---|
| 判别场景（旧回答"缓存"×4，当前回答不提；追问"缓存怎样更安全"） | **挂到讲缓存的那条** ✓（margin 0.08 即可） |
| 同一场景，margin 0.04 / 0.02 | 同样挂对 ✓ |
| 18 条标注（margin 0.08 / 0.04 / 0.02） | 14/18（三者相同，没有掉分） |
| 同义改写 8 条 | 3/8（不变） |

与 33b（改 evidence）相比：**这一版在默认边距 0.08 下就生效**，不需要动 margin，改动更小、更贴本意。
因此 33b 的 strong 改动与 margin 0.02 已回退，最终只保留 `discount = max(base, 占比)`。



## 实验 34：BGE（bge-small-zh）能不能解决同义改写

做法：`@huggingface/transformers` + `onnxruntime-node`（q8 量化），模型 `Xenova/bge-small-zh-v1.5`，
离线跑 `scripts/probe-bge.mjs`：对每条问题，用 BGE 向量给所有回答排序，看目标回答的名次。

| 集合 | BGE rank1 | 现有挂接（本地） |
|---|---|---|
| 18 条学习标注（去掉 root 项，17 条） | **1/17**（top3 4/17） | 14/18 |
| 同义改写 8 条（6 改写 + 2 控制） | **5/8** | 3/8 |

注意两点：

1. 标注集那一行**指标不完全可比**（BGE 是"排序"，本地是"实际挂接"），但它说明
   **单靠 BGE 排序无法替代现有规则**：长回答被 512 token 截断，向量只覆盖开头；
2. 同义改写上 BGE 明显更好：6 条改写里 3 条排第一（点乘/词的编号/配比那三条），
   而本地只挂对 1 条；2 条控制项都靠词面命中。

可行性数据（本机）：
- 模型加载 **96 ms**（q8，缓存后）；包体 @huggingface/transformers ≈ 10 MB + onnxruntime 原生二进制，
  模型下载 ≈ 25 MB（q8）；
- 环境有坑：直接 import `dist/transformers.js` 会因后端未初始化报 `reading 'create'`，
  必须走包名解析 `import('@huggingface/transformers')`；本机还有 CA 证书问题需要
  `NODE_TLS_REJECT_UNAUTHORIZED=0` 才能首次下载。

结论：BGE **只对"同义改写"这一种情况有可测收益**（6 条里 3 条），对长回答的整体排序很差。
是否接入取决于愿不愿意为"弱证据兜底"付出：原生依赖 + 约 25 MB 模型 + 首次下载。
未接入；探针脚本保留（需要临时安装依赖）。


## 实验 34b：BGE 分 chunk 再排序（含"ANN"说明）

做法：把每个回答按句子切成约 300 字的 chunk，逐块嵌入（`scripts/probe-bge-chunk.mjs`），
一条回答的分数有三种聚合：最佳块、Top-3 均值、全部块均值。18 个回答切成 **188 个 chunk**，
嵌入耗时 1,748 ms。

| 集合 | 聚合 | rank1 | top3 |
|---|---|---|---|
| 18 条标注（17 条） | best | 2/17 | 6/17 |
| 18 条标注 | meanTop3 | 1/17 | 5/17 |
| 18 条标注 | meanAll | 1/17 | 3/17 |
| 同义改写 8 条 | best | 3/8 | 5/8 |
| 同义改写 8 条 | meanTop3 | 3/8 | 4/8 |
| 同义改写 8 条 | **meanAll** | **5/8** | **7/8** |

对比不分 chunk 的版本（实验 34）：标注 1/17、同义改写 5/8。
**分 chunk 把标注的 top3 从 4/17 提到 6/17，rank1 仍然很差（2/17）。**

逐条看四个"本地挂错"的标注项，BGE 给目标的名次：3、9、4、13 —— 只有 1 项进 top3。
而同义改写的 6 条里，BGE 把 3 条排到第 1、2 条排到第 2–3。

关于 ANN：这个规模（188 个 chunk、8 个会话也就几千）**暴力余弦每查几毫秒**，用 HNSW 是纯机械负担；
如果真要上，也应当是"每节点嵌入一次 + 查询时暴力扫"，到十万级 chunk 再考虑索引。

结论：chunk 解决了"长回答被 512 token 截断"的问题，但**单靠 BGE 排序仍然远不如现有挂接规则**
（标注 2/17 vs 14/18）。它唯一站得住的用法是"当本地完全没有词面证据时的兜底"：
同义改写场景可从 1/6 提升到 3–4/6，代价是原生运行时依赖 + 25MB 模型 + 首次下载。


## 实验 35：把 BGE 相似度当 semantic 项（无差异，原因是评测集没有判别力）

做法：离线预计算"问题 × 回答"的 BGE 分块余弦（`scripts/build-bge-map.mjs` → `docs/experiments/bge-map.json`，
25 个问题 × 18 个回答），再让插件按环境变量读取该表，试了四种合成方式：

| 合成方式 | 18 条标注 | 同义改写 |
|---|---|---|
| 基线（无语义项） | 14/18 | 3/8 |
| 0.45·bge + 0.55·lexical | 14/18 | 3/8 |
| min(1, lexical + 0.5·bge) | 14/18 | 3/8 |
| 仅当 lexical=0 时用 0.5·bge | 14/18 | 3/8 |
| z 中心化后再合成 | 14/18 | 3/8 |

**五种完全一样。** 两个原因：

1. **评测集没有判别力**：18 条标注里 **1 条是 root、14 条是"停在上一回答"、只有 3 条需要"移动到更早的回答"**。
   任何打分改动最多影响那 3 条，而这三条 BGE 给出的目标名次分别是 **3、9、13** —— 修不好；
2. **BGE 余弦的绝对范围太窄**：同一问题对 18 个回答的余弦落在 **0.43–0.64**（均值 0.53），
   区分度本来就小；必须按问题做 z 中心化，但中心化后仍不足以改变决策。

结论：**现有评测集无法评估语义项**。要判断 BGE 值不值得接入，需要一套**只含"需要移动"样本**的标注集
（同义改写那 8 条正是这种集合，BGE 在那里 5/8 vs 本地 3/8）。代码已回退；预计算表和探针脚本保留。


## 实验 36：跳跃集（只含"必须移动"的样本）+ 三方对比

之前的评测集没有判别力（14/18 里 14 条是"停在上一回答"）。新建
`docs/experiments/jump-labels.json`：15 条问题**全部**需要挂到更早的回答上（同义改写 6 条、
回到早先解释 2 条、具体概念 7 条），追加在真实学习会话末尾，用扩展后的树评判。
脚本：`scripts/score-jump-labels.mjs`（每条独立重放，避免互相污染）。

| 方法 | 命中 |
|---|---|
| 现有本地挂接 | **6/15（40%）** |
| BGE 分块 · best | 7/15 |
| BGE 分块 · meanTop3 | 5/15 |
| **BGE 分块 · meanAll** | **11/15（73%）**，top3 12/15 |

这是第一份"语义方法明显优于本地规则"的公平对照。逐条看：本地 4 次把问题推到根，
5 次挂到错误的回答；BGE meanAll 有 11 次把正确回答排到第一。

但**不能直接替换**：同一会话里"停在上一回答"的 14 条，BGE 排序只有 1/17 排对
（实验 34/35）。所以正确的接法是**门控**：

```text
本地判断"该移动"或"没有证据"（当前会挂根/低分）时 → 用 BGE 选具体挂哪个
本地判断"留在原地"时 → 保持本地（BGE 在这里不可靠）
```

待测：按这个门控能把 15 条跳跃集做到多少，同时 18 条标注集不掉分。

## 实验 38：折叠的节流（cadence）——每 N 轮才允许折一次

**动机**：缓存是前缀式的，每次折叠都改写前缀。当前实现是在**每个 turn end** 重新判断
`historyTokens ≥ foldAboveTokens`，而 `historyTokens` 在重放里**不会因为折叠而下降**（实测：
折叠前后都是 3027），所以只要过了阈值，之后每轮都满足条件；真正限制频率的是"保留窗口之外
是否还有可折的轮"，短会话里每折一次只够腾出一轮，于是**每轮都折**。

日志证据（turn 间距）：

| 会话 | 轮数 | 破坏前缀次数 | 间距 |
|---|---|---|---|
| 3d7b782b | 305 | 13 | 5,8,41,31,36,16,22,1,63,64,2,1 |
| aa51835a | 22 | 9 | 5,4,1,1,1,1,1,1 |
| a2650e08 | 9 | 6 | 1,1,1,1,1 |

**实现**：新增 `foldCadence`（默认 3）。折叠前检查"距上次折叠已过几轮"，不足则不折；
只对 `foldPolicy: threshold` 生效（`always` 是显式要求每轮折）。设置页高级区可改，0 = 旧行为。

**模拟**（`scripts/probe-fold-cadence.mjs`）：先按会话实际折叠次数反推各自阈值（校准），
再在同一阈值下比较 N=1/3/5/8。成本按"折叠那轮整段重读、其余轮次缓存按 1/10"估算。

| 会话 | 轮 | 真实折叠 | N=1 | N=3 | N=5 | N=8 |
|---|---|---|---|---|---|---|
| 3d7b782b | 305 | 13 | 13 · 100% | 13 · 100% | 13 · 100% | 13 · 101% |
| 925c04be | 256 | 10 | 10 · 100% | 10 · 100% | 10 · 100% | 10 · 101% |
| aa51835a | 21 | 9 | 7 · 100% | 4 · **70%** | 3 · 65% | 3 · 65% |
| 102af94c | 76 | 4 | 4 · 100% | 4 · 100% | 4 · 100% | 4 · 100% |
| **汇总（6 会话 1170 轮）** | | | 54 · 100% | 51 · **99.6%** | 50 · 99.5% | 50 · 100.1% |

结论：

1. **长会话本来就折得很少**（20+ 轮一次），节流几乎不起作用（99.5–100.1%）；
2. **短会话是问题所在**（每轮都折），节流把它从 7 次降到 4 次，成本 −30%；
3. N 再大没有额外收益，反而让峰值变高（N=8 时 100.1%），所以默认取 3；
4. 这不是"省一半 token"的杠杆，而是**消除最坏情况**（每轮断缓存）的保险。


## 实验 39：折叠阈值改成"待折块"（相对保留窗口）

**语义变更**：`foldAboveTokens` 从"整段可见历史"改成"**准备折掉的那一块**"；
新增 `foldBlockRatio`（默认 5）要求块 ≥ 5× 保留窗口。两者取严：

```text
块 = 保留窗口之外、这次要移走的轮次 token 之和
保留窗口 = 折完后仍留在提示词里的轮次（会被按漏价重算的那部分）
折 ⇔ 块 ≥ foldAboveTokens 且 块 ≥ foldBlockRatio × 保留窗口（另有 foldCadence 轮数节流）
```

依据：命中价 = 漏价/50 时，一次折叠的代价 ≈ (1−1/50)×窗口，之后每轮省 (1/50)×块，
回本期 = 49×窗口/块；块 = 5×窗口 ⇒ 约 10 轮回本。

**离线对照**（`scripts/probe-fold-block.mjs`，9 个真实会话；两条规则都在同一套"每轮 token"上模拟，
折叠方式相同：窗口外的轮次各换成一个占位符）：

| 策略 | 折叠次数 | 成本（相对旧规则） |
|---|---|---|
| 旧：整段历史 ≥ 40k | 420 | 100% |
| **新：块 ≥ 40k 且 ≥ 5×窗口** | **44** | **68.7%** |
| 不折叠 | 0 | 391.3% |

逐会话看，长会话（305 轮）从 90 次折叠降到 11 次、成本 −14%；会话 102af94c 从 71 次降到 2 次、
成本 −60%。短会话（18–21 轮）基本不折了。

两条必须说明的边界：

1. "旧规则"这一列是**模拟重建**，不是日志里的真实折叠次数（真实是 4–13 次，因为各会话阈值不同），
   所以跨会话只看"同一模拟下新旧相对"；
2. "不折叠"= 391% 说明长会话里折叠是必要的，问题只在于**什么时候折**。

实现：`foldWorthIt` / `blockTokensOf` / `keptTokensOf` 是纯函数（见 `src/plugin/fold.ts`），
有单测；设置页把"历史超过多少 token"改成"待折的旧内容至少多少 token"，并新增"待折块至少是保留窗口的几倍"。


## 实验 40：真机 A/B 跑不起来 —— 当前宿主里折叠根本没发生

原本想用真机 A/B 定默认值，先做了一个 10 轮的脚本会话（3 个 arm：旧"整段历史"、新"块 + 5×窗口"）。
结果**三条 arm 的折叠次数都是 0**。这不是阈值没到，而是折叠路径在当前宿主上没跑通：

探针（临时 stderr）显示：

```text
TTFOLD enter {"hasAppend":"function","hasSurface":true}
TTFOLD state {"tokens":2798,"turn":3,"above":2000,...}
TTFOLD plan 0 visible 13 turnsOf=[[7,null],[8,1],[9,1],[10,1],...]
```

也就是说：

1. `session.append` 存在、surface 列表存在、阈值确实到了；
2. 但 `planTurnFold` 一个轮次都选不出来：宿主交给插件的 surface 事件**没有 turn 号**
   （user/message 没有 `data.turn`，surface 视图里也没有 turn/start），于是所有事件都被归到第 1 轮；
3. 日志里最后一次真实折叠是 **2026-11-03 23:04（本地）**，之后所有会话都没有再折过 —— 与宿主升级到
   0.2.1-rc.5 的时间吻合。

已顺手做的兼容改动（都带测试）：

| 改动 | 作用 |
|---|---|
| `service.seqTurns` + `turnOfSeq()` | 从插件看到的事件流里记住每个 seq 属于哪一轮 |
| `planTurnFold(..., turnOf)` | 事件没有 turn 字段时用上面的映射 |
| `session.eventAt` 声明 + surface 重建 | surface 有 seq 时按真实 seq 重建事件表 |

但真机上 turn 号仍然拿不到（surface 事件里 turn 全是 1），所以**折叠仍然不触发**。

结论：默认值这件事真机暂时测不了。离线模拟（实验 39）给的相对结论仍然成立：
块触发 + 5×窗口把折叠次数从 420 降到 44、成本 68.7%。默认值先按离线的取（`foldAboveTokens 40000`、
`foldBlockRatio 5`），等折叠在真机上恢复后再做一次端到端 A/B。
